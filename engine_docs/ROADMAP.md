# План развития движка QUEST-166

Дата фиксации: после тестирования 11 книг.
Основание: решения пользователя по пунктам 3.1–3.5, 3.6 (отложен), 4.1–4.4 и
этапам 1–4. Этап 5 — пилотная книга пользователя.

## 0. Цель

Обобщить опыт 11 книг и перейти от набора точечных механик к предсказуемой
архитектуре:

- контент отдельно;
- движок отдельно;
- UI отдельно;
- механики — через единый контракт;
- ошибки ловятся до публикации;
- новые книги подключаются без правок движка «под книгу».

## 1. Принятые решения

- **3.1** — подтверждено: разделить source/conversion, package, engine core и UI shell.
- **3.2** — подтверждено: один формат эффекта.
- **3.3** — подтверждено: один формат интеракции.
- **3.4** — подтверждено: механики как реестр, а не ветки в JSX.
- **3.5** — подтверждено: чистое ядро без React/DOM/localStorage.
- **3.6** — **отложен на потом** по решению пользователя. На этот прогон
  нормализация пакета на build-time не делается; текущая реализация остаётся
  runtime-парсингом.
- **4.1** — подтверждено: профиль книги и `features`.
- **4.2** — подтверждено: книжная специфика — в данных/миграциях, не в движке.
- **4.3** — подтверждено: preflight книги. Сейчас часть проверок идёт при
  парсинге, спорные случаи уходят в `review.md` и модерируются человеком.
  Целевое состояние — автоматический отчёт плюс ручная модерация сложных мест.
- **4.4** — подтверждено: CLI-симулятор/валидатор.

## 2. Этапы

### Этап 1 — низкий риск, общий UI-фундамент

Подтверждён. **Выполнен.**

Задачи:

- вынести общий компонент кубика:
  - pips 1–6;
  - числа больше 6;
  - общие тайминги;
- вынести общий keyboard-слой панелей;
- ввести `InteractionHost` для выбора интерактивного блока;
- убрать дублирование клавиатуры в панелях;
- не менять формат книг и механические формулы.

Критерий готовности:

- все книги открываются;
- проверки, ставки, магазины, Contest/Fallout-бой работают с клавиатуры;
- кубик одинаково выглядит во всех местах;
- сценарный бросок 1d6/1d15 показывает корректную грань;
- нет регрессий в существующих сценариях.

Подробно: [STAGE1.md](STAGE1.md).

### Этап 2 — чистое ядро и состояние

Подтверждён. **Выполнен.**

Задачи:

- вынести `resolve(state, action, rng)` из React;
- отделить эффекты от UI;
- ввести версию состояния и миграции;
- один боевой контракт с режимами `pool | contest | rpg`;
- один источник случайности с seed для тестов;
- убрать книжные ветки из `GameScreen` и `page.tsx`.

Критерий готовности:

- ядро тестируется без браузера;
- детерминированный прогон по seed;
- старые сейвы мигрируют;
- три боевых режима используют общий контракт.

Текущий статус: RNG, действия, версия состояния, миграции, выбор боевого
режима и чистые резолверы раундов для pool/contest/rpg готовы. UI-панели
пока сохраняют собственные оболочки.

### Этап 3 — формат quest/2

Подтверждён. **Схема зафиксирована; 11 книг сконвертированы в `quest2.yaml`;
старые `quest/1` удалены; адаптер не делается. Runtime `quest/2` ещё не подключён.**
Нормативная схема: [QUEST2_SCHEMA.md](QUEST2_SCHEMA.md), машинная:
[quest2.schema.json](quest2.schema.json). Валидатор:
`python3 scripts/quest2_validate.py <package>`.

Существующие 11 книг остаются `quest/1` без изменений; решение об их судьбе
принимается после всех изменений.



Задачи:

- описать схему `quest/2`:
  - типизированные эффекты;
  - типизированные условия;
  - интеракция как first-class объект;
  - `features`/`profile`;
  - видимость статусов;
- **адаптер `quest/1 → quest/2` не делаем**;
- созданы `games/<id>/quest2.yaml`;
- старые `quest/1`-файлы удалены;
- судьбу существующих книг (удалить, пересоздать, обновить или промежуточный
  вариант) пользователь решает после всех изменений;
- пилот — новая книга, которую выберет пользователь.

Критерий готовности:

- схема `quest/2` зафиксирована;
- пилот проходит JSON Schema и семантический валидатор;
- старые книги удалены, новые `quest2.yaml` прошли проверки.

### Этап 4 — AI-инструменты автора и разработчика

Подтверждён. **CLI и скиллы созданы.** Подробно: [STAGE4.md](STAGE4.md). Инструменты должны быть заточены под ИИ: скиллы с готовыми
командами/скриптами, а не только текстовая документация. Шаблон новой книги
не требуется.

Задачи:

- **AI-skills**:
  - `quest-validate` — схема, ссылки, достижимость, предметы, условия;
  - `quest-simulate` — случайные/умные прогоны, тупики, концовки;
  - `quest-graph` — граф и отчёт о достижимости;
  - `quest-convert` — конвертация и разбор `review.md`;
  - `quest-diff` — сравнение версий пакета/поведения;
- **CLI/скрипты**:
  - `validate`, `simulate`, `graph`, `convert`, `diff`;
  - машиночитаемый JSON-отчёт;
  - коды ошибок и приоритеты;
- **обновление QuestParser (корневой)**:
  - документация под новое ядро/формат;
  - правила и коды review;
  - эталонные примеры;
  - синхронизация с `engine_docs`;
- **обновление TestAI**:
  - тестовые сценарии под новый UI/механики;
  - генерация багрепортов;
  - проверки клавиатуры, мобильных, доступности;
  - регрессионный smoke всех книг;
- **обновление `engine_docs`** после каждого этапа движка.

Критерий готовности:

- ИИ может без человека прогнать валидатор/симулятор;
- отчёты читаются и человеком, и агентом;
- TestAI тестирует по актуальному контракту;
- документация QuestParser и engine_docs не расходятся.

### Этап 5 — пилотная книга пользователя

Пользователь выбирает книгу, которой ещё нет в библиотеке. Мы:

1. парсим её обновлённым инструментарием;
2. проходим preflight;
3. добавляем в библиотеку;
4. тестируем TestAI;
5. фиксируем пробелы инструментов и правим их.

Шаблон новой книги не создаётся: проверяем инструментарий на реальной книге.

## 3. Открытые вопросы

1. **3.6** — отложен на потом. Вернуться к выбору build-time/гибрида после
   конвертации книг и стабилизации `quest/2`.
2. Нужна ли обратная совместимость `quest/1` навсегда или только на переходный
   период.
3. На каком этапе переводить существующие 11 книг на `quest/2`.
4. Нужен ли отдельный пакет `@quest/engine` или монорепозиторий.

## 4. Правила этапов

- Не менять формат и механику без теста на всех книгах.
- Не делать книжную специфику в движке.
- Каждый этап заканчивается обновлением документации и smoke всех книг.
- Приоритет — сохранить играбельность, а не скорость переписывания.
