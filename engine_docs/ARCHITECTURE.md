# Архитектура движка QUEST-166

Версия документа: черновик после опыта 11 книг.
Статус: описывает текущую реализацию и целевые инварианты; целевая архитектура
вводится поэтапно по [ROADMAP.md](ROADMAP.md).

## 1. Назначение

Текущий runtime проигрывает `quest/1`; данные книг уже переведены в `quest2.yaml`,
поэтому до подключения `quest/2` старый загрузчик не находит `game.yaml`.

- читает манифест и необязательные файлы пакета;
- разбирает `story.md` в сцены;
- строит начальное состояние;
- показывает сцену и доступные интеракции;
- применяет выборы, проверки, бои, ставки, коды, магазины и эффекты;
- сохраняет состояние в `localStorage`.

Движок не является редактором книг. Конвертация PDF/TXT/HTML в пакет — задача
QuestParser; движок получает уже собранный пакет.

## 2. Слои

Сейчас фактически есть четыре слоя:

```text
Пакет на диске (games/<id>/)
        ↓  /api/games
Загрузчик (lib/games.ts)
        ↓
Парсер и валидация пакета (lib/parse.ts)
        ↓
Модель Game + GameState (lib/types.ts)
        ↓
Чистые операции состояния (lib/engine.ts)
        ↓
React-экран (components/screens/GameScreen.tsx и панели)
        ↓
localStorage (lib/storage.ts)
```

Целевое разделение:

```text
1. Source / conversion  — QuestParser, вне runtime
2. Package quest/2      — нормализованные данные
3. Engine core          — чистый reducer без React/DOM
4. UI shell             — сцена, InteractionHost, панели, клавиатура
```

После этапа 2 внутри runtime появились:

- `lib/rng.ts` — единый seedable RNG;
- `lib/actions.ts` — чистые действия игрока;
- `lib/migrations.ts` — версия состояния и миграции;
- `lib/combat.ts` — контракт выбора боевого режима.

## 3. Пакет книги

Обязательные файлы:

```text
games/<id>/
  game.yaml      манифест: метаданные, start, список сцен и их переходы
  story.md       текст сцен: ## <scene>, варианты, отсылки
  assets/        обложка и иллюстрации
```

Необязательные файлы, объявляемые в манифесте:

```text
items.yaml       предметы
stats.yaml       статусы
flags.yaml       объявленные флаги
mechanics.yaml   checks / gambles / combat
codes.yaml       коды «параграф ± число»
```

Манифест содержит:

- паспорт книги: `id`, `title`, `author`, `genre`, `status`, `annotation`;
- режим: `type` (`storybook`, `fighting-fantasy`, `rpg`, `hybrid`);
- точку входа `start`;
- пути к необязательным файлам;
- `moods`;
- сцены: `title`, `mood`, `image`, `next`, `variants`, `ending`,
  `on_enter`, `shop`, `shopTitle`, `shopCurrency`.

## 4. Загрузка и парсинг

`lib/games.ts`:

1. `GET /api/games` — индекс библиотеки. API читает `games/*/game.yaml` и
   `story.md`, отдаёт `id`, `title`, `author`, `genre`, `type`, `status`,
   `annotation`, `updatedAt`.
2. `loadGame(id)`:
   - читает `game.yaml`;
   - параллельно запрашивает объявленные `items.yaml`, `stats.yaml`,
     `flags.yaml`, `mechanics.yaml`, `codes.yaml`;
   - потоком читает `story.md` (для BOOK LOADER);
   - передаёт всё в `parsePackage`.

`lib/parse.ts`:

- разбирает `story.md` на секции `## <key>`;
- собирает варианты, отсылки и `next`;
- накладывает метаданные сцен из `game.yaml`;
- читает предметы, статусы, флаги, проверки, ставки, бои и коды;
- валидирует ссылки, условия, цели, идентификаторы и поля;
- возвращает `Game` и список `ParseProblem`;
- вычисляет `rev` — отпечаток текста, чтобы старые сейвы не применялись к
  изменённой книге.

Проблемы разбора показываются в `.parse-report`, а не только в консоли.

## 5. Состояние

`GameState` — сериализуемый объект с версией схемы:

```ts
{
  game, format, version, rev,
  scene,
  inventory,
  flags,
  knownCodes,
  gamblesDone,
  stats,
  initialStats,
  visited,
  updated
}
```

Правила:

- состояние неизменяемое: операции возвращают новый объект;
- `visited` хранит историю посещений;
- `knownCodes` и `gamblesDone` — механические журналы, а не «статы»;
- `initialStats` нужен для лечения до стартового уровня;
- сохранение — `localStorage` по ключу `quest:save:<id>`;
- настройки — `quest:settings`;
- актуальная версия — `STATE_VERSION = 2`;
- старые сейвы проходят `migrateState` в `lib/migrations.ts`.

## 6. Движок

`lib/engine.ts` — чистые функции:

- `newState(game, rng)` — начальное состояние;
- `sceneOf(game, state)` — текущая сцена;
- `availableChoices(game, state)` — доступные варианты;
- `choose` — применить выбор;
- `advance` / `resolveRoll` — линейный переход и бросок сцены;
- `goToScene` — переход с эффектами входа;
- `useCode` — применить код;
- `isEnding` — проверка концовки.

Действия игрока собраны в `lib/actions.ts` (`applyAction`): выбор, переход,
назад, код, ставка, проверка, покупка, победа в бою. UI вызывает действие и
сохраняет результат; арифметика состояния находится в ядре.

### Эффекты входа

`on_enter` — упорядоченный список эффектов:

- `if` — условие;
- `take` / `drop` — предметы;
- `stat` / `statRoll` — статусы;
- `set` — флаги;
- `use` — расход предмета;
- `learn_code` — изучить код;
- `dropBestWeapon` — удалить лучшее оружие;
- `goto` — условный переход.

`take` в `on_enter` срабатывает только при первом входе в сцену. Эффекты на
выборе срабатывают при каждом выборе.

### Условия

Строковый DSL:

```text
stat money >= 100
has_item pistol
not has_item pistol
flag heart_up_19
and / or / not
```

Проверки условий и выражений сосредоточены в движке; UI не интерпретирует
формулы.

## 7. Интеракции

Сейчас `GameScreen` определяет, что показать, по данным сцены:

1. бой (`combat`);
2. проверка (`checks[scene]`);
3. ставка (`gambles[scene]`, если ещё не сделана);
4. магазин (`shop`);
5. концовка;
6. варианты;
7. кнопка «ДАЛЕЕ»;
8. бросок сцены (`next.roll` и outcomes).

Порядок приоритетов — часть контракта, а не случайность. Его нельзя менять без
тестов.

### Бой

Сейчас три режима в трёх компонентах:

- `CombatPanel` — классический FF-бой (Зомби, Steel Rat);
- `ContestCombatPanel` — контестный бой Orcsday:
  `2d6 + стат + рейтинг` против Защиты, попадание = 1 Здоровье;
- `FalloutCombatPanel` — Fallout:
  `d20 + навык` против Защиты, урон оружия, броня, несколько врагов.

### Проверки

`CheckPanel`:

- FF: `2d6 + стат` против выражения;
- RPG: детерминированная проверка способности/навыка;
- Fallout: проверка навыка списывает мораль `(1d6 − навык) × 4`.

### Ставки

`GamblePanel`: ставка, `2d6 + стат`, полосы `win` / `push`, изменение денег,
запись в `gamblesDone`.

### Коды

`knownCodes` + панель «КОДЫ»; цель = `(base ?? currentScene) + offset`.
Код не является статическим ребром графа.

### Магазины

`ShopPanel`: список `shop`, цена, валюта, покупка через `money`.

## 8. UI и события

В «Крови зомби» боевая панель использует библиотеку
`assets/zombies/zombies.json`: пассивный зомби, три кадра атаки и кадр смерти.
Иконка зомби и текущего оружия стоят справа от боевого лога; между ударом
игрока и ответом врага есть пауза, анимации привязаны к фазе боя.

Боевые действия во всех режимах (pool/contest/rpg) используют латинские
хоткеи A/B/C/D. Верхняя строка боя показывает только номер раунда, а количество
врагов и жизни персонажа пишутся в лог в конце каждого раунда.

`GameScreen` — контейнер экрана. Для статов/инвентаря есть два режима:

- до двух видимых статов и/или объявленных предметов — компактный HUD в шапке;
- больше двух — прежние всплывающие панели.

В шапке каждой книги есть кнопка инструкции. Если в пакете есть сцена
`rules`, открывается её текст; иначе используется стандартная инструкция по
типу книги (`storybook`, `hybrid`, `fighting-fantasy`, `rpg`).

В библиотеке обложка показывается миниатюрой; клик открывает увеличение. При
старте книги с обложкой первая страница — обложка с кнопкой «ЧИТАТЬ»; для
Zombie Blood она стоит до стартового броска.

В Zombie Blood деньги (`money`) — предмет инвентаря, а не статус; магазин может
использовать `currency_item` и списывать предмет напрямую.

`GameScreen` — контейнер экрана:

- шапка: название сцены, правила, коды, характеристики, инвентарь;
- `.scene-scroll`: изображение, текст, интеракции;
- нижние действия: бой, магазин, варианты, «ДАЛЕЕ», бросок;
- модальные окна: правила, зум изображения;
- глобальная клавиатура: цифры, Enter, стрелки, Esc.

Интерактивные панели используют общий `usePanelKeys` (capture-фаза), чтобы не
конфликтовать с общей клавиатурой `GameScreen`. `InteractionHost` выбирает
проверку/ставку/бой; магазин и нижние действия пока остаются в `GameScreen`.

## 9. Кубики и анимация

- грани 1–6 рисуются точками;
- значения больше 6 — числом;
- сценический бросок: 1,3 с прокрутки + 1,4 с финального результата;
- боевые кубики имеют собственные тайминги и анимации;
- общая грань — `components/screens/Dice.tsx` (pips 1–6, число >6).

После этапа 1 pips и keyboard-слой общие; боевые тайминги пока остаются
собственными у каждого режима.

## 10. Сохранения и версии

- версия книги — `rev` по тексту `story.md`;
- при изменении `rev` старый сейв может быть сброшен;
- `repairSceneItems` в `app/page.tsx` — временный миграционный слой для
  Zombie Blood; в целевой архитектуре такие вещи должны жить в миграциях
  пакета, а не в UI-контейнере.

## 11. Текущие архитектурные ограничения

1. `GameScreen` знает слишком много о механиках и книгах.
2. Три боевых движка; кубик и keyboard-слой уже общие.
3. `parse.ts` смешивает парсинг, нормализацию, валидацию и книжные компенсации.
4. Нет единого build-time валидатора достижимости и целостности.
5. `repairSceneItems` и отдельные проверки по `game.id` / `scene.key`.
6. Сейв-схема без явной версии и миграций.
7. Формат `quest/1` растёт полями «под случай», без единой модели эффекта и
   интеракции.
8. Runtime парсит YAML в браузере при каждом запуске книги.
9. Боевая математика раундов вынесена в `lib/combat.ts`; у трёх панелей пока
   остаются собственные UI-оболочки и анимации.

## 12. Целевые инварианты

1. Движок не знает `id` книги, ключей сцен и названий предметов.
2. Любая интеракция — зарегистрированная механика со схемой, runtime и UI.
3. Любой эффект — типизированная операция, а не произвольный набор полей.
4. Ошибки книги ловятся до публикации, а не в браузере игрока.
5. Один кубик, один keyboard-слой, один боевой контракт.
6. Состояние версионируется и мигрируется.
7. Контентная специфика хранится в данных или миграциях, не в JSX.

## 13. Как добавить новую механику

Сейчас:

1. добавить поле в `types.ts`;
2. научить `parse.ts`;
3. добавить ветку в `engine.ts`;
4. добавить панель и ветку в `GameScreen`;
5. добавить CSS и клавиатуру;
6. добавить тест вручную.

Целевой порядок:

1. описать схему данных;
2. реализовать runtime-функцию;
3. зарегистрировать UI-адаптер;
4. добавить валидатор;
5. добавить симулятор/тест;
6. подключить в пакете через `features`.
